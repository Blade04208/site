1. From a birds-eye-view

1.1. DHH's "Distro"

One topic brought up so often is whether Omarchy is even a "distro" or not. I feel like we need to define what a "Linux Distro" is here, to be fair.

A Distro, according to Wiktionary in terms of software, is

A set of software components, often open source, that have been packaged into a larger product or component for distribution to end-users.

We should also probably define Software too.

Encoded computer instructions, usually modifiable (unless stored in some form of unalterable memory such as ROM). Some software will only run on a particular platform.

Encoded is defined here as translated to code, defined as

  1. (programming, uncountable) Instructions for a computer, written in a programming language; the input of a translator, an interpreter or a browser, namely: source code, machine code, bytecode. Object-oriented C++ code is easier to understand for a human than C code. I wrote some code to reformat text documents. This HTML code may be placed on your web page.

I think it's safe to say Omarchy's Bash scripts are software, but are they packaged? Packaged is defined as

  1. (software) A piece of software which has been prepared in such a way that it can be installed with a package manager.

After some digging, omacom-io/omarchy-pkgs has pkgbuilds and is a packaging server for omarchy, so if you were to put the omarchy package server onto a vanila arch install, you could install omarchy packages.

This obviously isn't conclusive, and will never be to some people, and that's fine. It's just what you want to name a thing. This section is completely frivolous compared to some of the other sections, to be honest. If you want another (probably more reputable) person's opinions on this, Brodie Robertson also made a video about this topic while i was writing this.

Actually, looking at these Omarchy scripts for a second... what the hell are these?

1.2. Omarchy's software

I'm explicitly discussing Omarchy's own script files here, not software in their menu.

Omarchy's scripts are weird. Instead of DHH (or, well, more likely his 5 AI agents - we'll get to that later,) using the practically global standards for dotfiles, he's making the scripts and apps himself? Look at omarchy-notification-send. This is a notification sender that does so through the notification D-Bus socket, but this is really strange because this software already exists, it's called notify-send, a part of libnotify, the notification standard that a substantial amount of Linux software uses, and literally comes with Omarchy by default.

Why not use this?? Does he have beef against specifically notify-send? As far as I can see, omarchy-notification-send adds no new features that notify-send doesn't already have, why is this here?

You know, I was halfway through these scripts when I realized, its not DHH being an idiot or having grudges against all software, it's branding. omarchy-pkg-install-aur exists because when someone on arch wants to install an AUR package someone from Omarchy recommended to them, they'll go "oh, its omarchy pkg install helium" which obviously the Arch user won't have. When the Arch user says "what's the actual command behind that" the Omarchy user won't know, because they're a beginner to Linux who just installed someone's riced up arch setup because they were told it's "user-friendly" and "welcoming" and "apolitical unlike the REST of these Linux goblin spaces" (WE WILL GET TO THAT LATER.) but ultimately Omarchy leaves them with skills they can't take back out of Omarchy, so they stay. This is really bad for growth, community and interoperability between Linux users. Obviously this is a bit over-exaggerated, the Arch user would likely know to just yay -S it, but DHH wants Omarchy to become the face of the Linux Desktop, so stuff like this is gonna happen to newcomers.

One last thing about these scripts. This could have been just one binary man. omarchy already maps to every other bash script in bin/, so just compiling this into one binary in your language of choice would save having to go down the ladder of scripts, and would make it easier for other distros to package omarchy, which could allow you to "omarchify" any distro, which might be quite cool as a concept!

1.3. (A lack of) Security

So it turns out when you package and manage your entire system through bash scripts and AI agents, a few small cracks appear.

Remember that notification bash script? Someone figured out how to exploit that to run arbitrary code. Some{one|bot} forgot to cleanse their strings! This isn't the only security vuln disclosed over Twitter, there's also the fact that Omarchy gives you the root docker socket on install, and with an RCE like above you can do some really dangerous stuff. Now, Omarchy does have a team dedicated to security, and a deliberate contact page for security vulns, https://omarchy.org/security/, and a responsible-disclosure policy, but that page was only made with Omarchy 4.0.1, after these critical security bugs were found. As a matter of fact, it hasn't appeared that Omarchy actually disclosed their own vulnerablilites on a dedicated page, which is really bad for a project that's meant to become the "face of the Linux Desktop".

I haven't even got to the funniest part here. That notification exploit? That was figured out by someone who is now in Omarchy's brand-new security team, and instead of doing the responsible thing here and telling the Omarchy team privately, he disclosed it on Twitter, which manages to get him onto the Omarchy Security team because yes, disclosing vulnerabilities on Twitter is the sign of a good security specialist, uh-huh.

As a sidenote, yes, I do know Mehmet Ince is a real security resarcher with real CVEs, but revealing a giant secuity flaw on Twitter instead of proper disclosure in my opinion shows that Mehmet didn't take Omarchy seriously, which makes me question why DHH picked him.

For anywhere that security is involved, for Omarchy to become a serious contender, they should preferrably

  1. Disclose their security vulnerablities only after shipping them
  2. Preferrably notify all users about said vulnerability and ask them to update their packages. I really can't reccomend Omarchy for anything security-involved otherwise.

However, to be fair to DHH, he managed to get an entire security team, contact page, credits page and get the bugs fixed in less than a week, which I have to commend him for.

2. Feet On the Ground

2.1. Installing Omarchy

Whilst I was writing this, I thought it be best to actually try out Omarchy instead of just talking without looking. The install ISO is 6.8GB, which seems a bit excessive, I would enjoy an actual installer where you can select the components you want, and also extra components (e.g install spotify as a postinstall job, etc), and it might even cut down a little bit on install times! On entering the system, it asked me to choose an AI model and if i wish to install speech dictation, but other than that, setup was done, and I do have to say, this is quite well-made.

2.2. Using Omarchy

The shell is quite well put-together, and nothing feels truly out of place. I have a few minor gripes with the launcher, but that's just mostly personal taste (I like wider searchbars.)

A lot of menus go directly to some bash script, which while bash is great, I adore native UI, so having a dialog box for "Do you want to uninstall all pre-installed software" (Another good feature to have, btw!) feels better to me than a terminal prompt for it. Still, that's just personal preference.

A thing I do commend though is the "learn" section. Having quick shortcuts to essential guides is really damn nice to have, and is great for beginners.

I would really love to customize the Omarchy menu more, pin stuff and make custom sub-menus, even.

Other than that, Omarchy is a great pre-setup experience on the outside. I haven't done a deep dive into it, I don't have time to, sadly. But if someone threw me in front of an Omarchy machine, I wouldn't be frustrated.

3.3. An irrefusable offer

Omacom's first order of business was to exclusively and premierely sponsor Vaxryy and Outfoxxed respectively, creators of Hyprland and Quickshell respectively, and also terminating Hyprperks, Hyprland's paid official dots, forum access and Q&A. That word is important there, exclusively. As quoted in the Omarchy news post about hyprland:

Many thanks to 37signals (hello self! 😂), Butterfly, and Framework for helping Hyprland get to this point. Thrilled that the Omacom Foundation can take over from October 10, and give one of the best developers in this new Linux moment the chance to go all-in.

This confuses me. Why is this exclusive? Well, you could either take this from a cynical, malicious point of view or an innocent point of view. On the innoncent side:

  • Full funding implies exclusivity anyway - If you're paying a maintainer enough to "never think about fundraising or commercial development again" (DHH's words), letting him simultaneously take a second corporate sponsor creates unresolvable conflicts of interest. Formalizing it as exclusivity is just honest bookkeeping.
  • Buyout logic. You can't terminate someone's paid perks program while permitting them to sell equivalents elsewhere. Exclusivity is the contractual consideration for ending Hyprperks - it protects Omacom from paying for a maintainer who's still monetizing independently.
  • Clean governance - One patron = one accountable party, no divided loyalty when priorities collide. Multi-sponsor maintainers genuinely do get squeezed.
  • Multi-year predictability - 3-year terms let both sides commit to roadmaps without re-negotiaotiaion or pulling out mid-way through.

But these points apart from the last, perhaps, don't make sense for a sponsor of a FOSS project as being a sponsor doesnt mean you get any kind of decision power in most cases, and it appears to be the same for Hyprland, too. Which brings us to the possibly more malicious reasons.

  • Aquisition-less Aquisition - Hyprland and Quickshell are Omarchy's desktop identity. Total financial dependence converts two community projects into something functionally close to contracted suppliers but with no equity, no IP assignment, no employment law, but Omacom is the only entity that can turn the money tap on or off. Cheaper than hiring, stickier than a grant.
  • Rival influence lockout - Non-exclusive deals would let any other company or foundation "buy" the compositor and shell toolkit at the heart of Omarchy. Exclusivity locks the door behind them.
  • Ideological lock-in - Both recipients were picked partly because they're outside the Code-of-Conduct-governance establishment (We will discuss that). After three years of sole-source income, neither can credibly criticize their patron without torching their own livelihood. That's soft power no contract clause needs to state.
  • The roadmap dependency - The Quickshell announcement explicitly ties the money to "cement the connection to our long-term plans for The Age of Agents." Quattro's whole design needs tight compositor-to-shell coupling; guaranteed developer attention on Omarchy-relevant work is precisely what's being purchased. Diffused priorities across multiple patrons would dilute that.

Exclusivity is essentially unheard of in mainstream OSS funding norms like Sovereign Tech Fund, NLnet, GitHub Sponsors and corporate foundations, all of which ate non-exclusive by default. Exclusive multi-year personal sponsorship is standard practice in exactly two domains, being sports and the creator economy via athlete endorsement deals and streamer contracts. DHH is a Le Mans racing driver who runs a media operation, as far as I can see he imported the motorsport/creator deal structure into FOSS and used it as-is. DHH even jokingly called it the "Oligarchy" distro and bought a domain for it, oligarchy.fyi.

In my opinion, nothing good can come from this exclusivity. Note what innocence can't explain away: why pick the two co-working projects Omarchy depends on, make them financially monogamous with oneself specifically, and pair it with trademark-holding, unless control of those dependencies is the point.

Vaxryy says his authority over Hyprland's direction is preserved, and there's no public evidence of feature strings today. The risk isn't what's in the contract; it's that in year four, "renewal" and "independence" become mutually exclusive concepts for a man who gave up every other income stream. I'm not saying that's what's going to happen, I'm saying that it could. I'm not saying this is DHH's plan or "agenda", im saying that this is a possibility that can only come from exclusivity.

Let's go to something not as heavy and forboding with the possibility to ruin people's lives, jobs and welfare. Let's talk about AI.

3.4. DHH (probably) doesn't know his own codebase

It's no secret that DHH vibecodes Omarchy, and he presents it proudly, claiming Omarchy is more malleable because you can ask an agent to change anything on your system. This is actually a really cool concept, where all of your system is configurable from one "prompt". However, DHH uses a bit more than one prompt, or even just one agent.

That there is DHH, Omarchybot, Claude and Codex (xhigh) in one commit. From the description of this commit, its clear that this was done over at least multiple claude sessions, but probably multiple of all of the AI agents here. The manual for Omarchy and its code is clearly vibe-coded, so that raises the question - is this DHH's own codebase? Does he know what's in his distro, or is it so abstracted away with AI agents that he has no clue what's making his system tick? It's probably a mix of yes and no. The problem with an abstracted codebase like this is that if you encounter an issue, you never coded the bug, wouldnt know where it is, and wouldn't know how to fix it, because you delegated it to your agents. Additionally, by working in this way, your ability to program is only whenever your agent's providers are not under maintenance and if you have enough usage left. If they don't, they're clocked out for the day, and you're left as a boss with no employees.

Another problem with dotfiles is that they're spread so thinly throughout your system, so either you modify files on the fly, or you put them into one centralised codebase which then "re-builds" itself and puts all the changed files where they need to go. It turns out this already exists, and its called Ni- oh, DHH already knows about this? Let's hear his thoughts on it! I'm sure it'll only be a matter of time before he starts using it!
